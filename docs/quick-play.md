# Quick Play

Solo remains local and untimed. Quick Play chooses starting chassis before queueing. A single FIFO queue starts when four humans join, or 120 seconds after its oldest waiting cohort begins. Remaining seats get seeded bot profiles. No private rooms, registered accounts, custom names, chat, skill divisions or progression.

Server owns all drafts, combat outcomes, ranking and HP. Human draft turns receive a fresh 20 seconds; no unused time carries forward. Each consecutive timed-out turn auto-picks and reduces the next allowance by three seconds, with a five-second floor. Any timely manual selection resets the streak and restores 20 seconds for the following round. Disconnects do not pause time; returning via the same browser tab's session token restores the seat. Explicit leave transfers seat to bots immediately. Queue cancellation is free. Inactive queued sessions expire after 20 seconds without polling; all-abandoned matches and finished sessions are eventually cleaned up.

Transport: same-origin HTTP JSON, revision-checked picks, opaque bearer tokens in sessionStorage, 500 ms polling; unchanged revisions return only clock/phase metadata. Only legal actions and public match state are transmitted. Public generated nicknames only; no cross-origin access or chat. Client replays seeded combat with server time and never submits results. Server computes one full deterministic round, publishes its starting state and releases its authoritative result at round end, then advances after three seconds. No continuous position traffic. Slow clients may catch up or skip to authoritative results; visual parity on different phones still needs real testing.

Run: Node 22+, npm start (PORT defaults 3000), open the served URL. npm test covers queue, clocks, reconnect, revision and authorization. Railway serves the same game from main at https://quick-play-production-4fff294f.up.railway.app/ with one replica and /health. The old public GitHub Pages link redirects to the hosted game; local static serving supports Solo only. Ranked is visible but unavailable; Options groups graphics, display, private match history and optional telemetry. The launch menu retains only play actions, including Resume Solo when available. Live queues/matches remain in memory and restart loses them; 16 match and 256 session safety limits. Opted-in completed Quick Play results persist in SQLite. Session recovery applies to a refresh in the same tab, not an arbitrary device. HTTPS should terminate at hosting provider.

Optional playtest statistics: unchecked Options > Privacy & playtest statistics checkbox; enabling stores only the preference locally. A random in-memory page-session ID groups cumulative foreground seconds (by Solo/Quick Play) and starts/completions/explicit exits; hidden tabs, queue/menu time, paused Solo combat and eliminated spectators do not count. Page refresh creates a new ID. No account credential, seed, IP, user-agent, game actions or session token is included in application telemetry. Opted-in sessions with a valid guest cookie include a server-derived analytics-only pseudonym (playtest_session_v2). Consent must be given again after the 3.7 update; old anonymous sessions remain unlinked; the legacy /api/playtest route never attaches guest identity. Same-origin /api/playtest/guest validates bounded snapshots and caps accepted events at 600/minute globally. Railway logs contain playtest_session_v1/v2 events; use the greatest seq for each id, never sum cumulative snapshots. The last snapshot is best-effort on hide/exit, with a 60s heartbeat; browser crashes/network errors can undercount and opted-in players are not representative of all visitors. No third-party SDK; analytics remain separate from the match history database. Hosting log retention and access are managed by Railway; avoid exporting individual session rows publicly.

Guest profiles: POST /api/guest issues or renews a signed 365-day first-party HttpOnly SameSite=Lax cookie (Secure on Railway); the public nickname is generated deterministically from the random guest ID and signing key. Name collisions are possible and do not determine identity. Railway requires a stable GUEST_SIGNING_KEY; local development without it uses an ephemeral key. Queue and active match admission are guarded by guest ID, not nickname or IP. Every HTTP Quick Play action requires the matching cookie plus the existing per-tab bearer token, except join which requires just the cookie. Same-browser additional tabs cannot occupy another active seat; refresh in the original tab uses its existing token. Explicit leave releases the seat; finished matches no longer block admission. Web Locks serializes initial guest issuance on supported browsers. Clearing cookies, private browsing, separate browser profiles and other devices can create new guests. No fingerprinting or IP restrictions. No persistent account database yet; a future account service can associate the authenticated guest ID with an account. Clearing browser cookies loses guest access; key rotation invalidates cookies and changes the derived analytics namespace. Guest-linked analytics remains opt-in and is separate from necessary matchmaking identity; hosting proxy logs are outside application telemetry.

## Persistence and security
Node 22.13+ built-in SQLite, one replica, database at RAILWAY_VOLUME_MOUNT_PATH/history.sqlite (or HISTORY_DATA_DIR locally; in-memory without either outside Railway). Production refuses startup without a durable mount. The guest cookie remains the credential; optional private history is indexed by authenticated guest ID, with 100 recent completed matches and lifetime totals. Consent must precede queue entry and still be enabled at match finish. No browser-submitted scores, no opponent names or match replay tokens in history responses. Turning history off deletes its rows and totals; history and analytics consent are separate. Capacity 10,000 opted-in guests; no account linking or active Quick Play recovery across deploys yet. Solo checkpoint is local, automatically saved before combat or at a draft boundary; restoring combat restarts that round deterministically, not mid-frame. Solo history is separate, opt-in, local and capped at 100 results. Checkpoints are versioned by engine rules; discard invalid or incompatible saves. No server upload of Solo results. Guest/profile routes enforce same-origin fetch metadata, Origin host checks and bounded JSON; SQLite uses bound parameters; HTML uses textContent; CSP blocks inline scripts and framing. Global guest issuance/history-write budgets are coarse abuse protection, not comprehensive DDoS defense. Before any player text, require bounded schema, output encoding, identity-based limits, moderation/reporting where applicable, abuse tests, and account-specific authentication/recovery review. Backups and restore drills are still needed.
