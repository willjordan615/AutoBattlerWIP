# Optional profiles (4.2)
Guest play stays unchanged. An optional account uses a server-generated 256-bit recovery code (ab1_ plus 43 base64url characters) shown once on creation; no email, password or required personal information. Account creation preserves the server-generated nickname and atomically moves opted-in Quick Play history and lifetime totals to a new random account ID. Signing into an existing account leaves the local guest profile and its history separate. Solo checkpoints/history, telemetry consent and graphics/audio settings stay local. No public profiles or ranked mode yet.
Server stores SHA-256 digests of random recovery codes and opaque 256-bit session tokens, not the credentials themselves. Separate HttpOnly, SameSite=Strict, Secure-on-Railway account cookie, fixed 30-day expiry, maximum eight sessions per account; sign-out revokes current session, deletion requires the recovery code and removes the account, history and all sessions. Guest cookie cannot authenticate an account. Existing origin checks, JSON size/shape validation, bound SQLite queries, generic failures and global account-write budget (60/min) apply. Account capacity 10,000. No IP/fingerprint tracking or code logging. One active seat per effective identity; profile switching is blocked while queued/in an unfinished online match. Multiple separate identities still possible; this is not strong anti-smurf protection. No email recovery or recovery-code rotation yet; lost code plus expired sessions means loss of account access. Recovery code should be stored privately.
SQLite schema v3 is additive on the existing persistent history volume. Preserve and back up the database before operational migrations; rollback to v1 binary requires restoring a compatible backup. No account data is sent to clients other than display name/account status, and the one-time recovery code. Security review is preliminary, not an independent penetration test. Before chat or public profiles, add reporting, human moderation, stronger per-client abuse controls, and a recovery/revocation workflow.

Initial isolated Node 22/SQLite verification ran against the exact server/accounts.js blob: account creation, history transfer, persisted login, hash storage, session limit, expiry, revocation and deletion passed. Full HTTP and client regression coverage is supplied in the repo tests; independent security review and production backup verification remain outstanding.

Account names: optional customization after creation; 3–16 ASCII characters, initial letter, letters/digits/underscores. Server assigns a globally unique four-digit tag on first customization, retained on subsequent renames; tags are released on deletion. Generated names remain unchanged until customized. Server-only limited English profanity/abuse and reserved-role filtering with simple normalization; false positives and missed terms are possible. A successful change starts a 24-hour cooldown; exact no-op is allowed. No changes while queued or in a match. Public display only, never used for authorization. Avoid real names, contact details and identifiers. The reviewed game display sinks use textContent or safe attribute assignment. SQLite v3 adds the tag table without altering existing identities or histories.
